ข้อ 1 + 3: Shneiderman’s Eight Golden Rules

กด “แบบมีปัญหา” แล้วลองส่งฟอร์ม จากนั้นสลับเป็น “แบบแก้แล้ว” เพื่อเทียบ

เดโม: ฟอร์มสมัครสมาชิก
เดโม: รายการงาน (ข้อ 2 shortcut, 3 feedback, 6 เลิกทำ, 7 ควบคุมเอง)

พิมพ์แล้วกด Enter เพื่อเพิ่ม · กดปุ่ม N เพื่อกระโดดไปช่องพิมพ์ · ลบแล้วกด “เลิกทำ” ได้

ยังไม่มีการกระทำ ลองเพิ่มหรือลบงานดู

ทั้ง 8 ข้อ (กดเพื่อดูตัวอย่าง)

1. Strive for consistency

ใช้คำ สี ตำแหน่งปุ่มเหมือนกันทุกหน้า เช่น ปุ่มหลักสีเดียวกันและอยู่ขวาล่างเสมอ

2. Seek universal usability

รองรับมือใหม่ถึงผู้เชี่ยวชาญ ผู้สูงอายุ ผู้พิการ เช่น shortcut, ปรับขนาดตัวอักษร (ฉบับเก่า: Enable frequent users to use shortcuts)

3. Offer informative feedback

ทุกการกระทำต้องมีผลตอบกลับ เช่น loading, “บันทึกสำเร็จ”

4. Design dialogs to yield closure

ลำดับงานมีเริ่ม กลาง จบ เช่น หน้า “สั่งซื้อสำเร็จ” หลัง checkout

5. Prevent errors / simple error handling

ออกแบบไม่ให้ผิดตั้งแต่แรก เช่น dropdown วันที่, disable ปุ่มจนกรอกครบ

6. Permit easy reversal of actions

Undo, ถังขยะกู้คืนได้ ผู้ใช้กล้าลองเพราะไม่กลัวพลาด

7. Keep users in control

ผู้ใช้เป็นผู้ควบคุม ไม่ใช่ระบบ เช่น ยกเลิกหรือออกจากขั้นตอนได้ตลอด

8. Reduce short-term memory load

ให้เห็นแทนการให้จำ เช่น autocomplete, สรุปรายการก่อนยืนยัน

แบบทดสอบข้อ 1+3

ตัวอย่างการตอบ

“ฟอร์มแจ้ง error หลังกดส่งเท่านั้นและไม่บอกว่าช่องไหนผิด” → ละเมิดข้อ 3 (Feedback) และข้อ 5 (Error handling) → แก้โดย validate แบบ real-time ชี้ช่องที่ผิดพร้อมข้อความบอกวิธีแก้

ข้อ 4: Evaluation (Nielsen’s 10 Heuristics)

จับผิดหน้าจอจริง เลือก heuristic ที่ถูกละเมิดในแต่ละกรณี แล้วกดตรวจ

เดโม: Heuristic Evaluation
เลือกคำตอบทุกข้อแล้วกดตรวจ

Evaluation คืออะไร

Evaluation คือการประเมินว่า interface ใช้งานง่ายแค่ไหนและมีปัญหาตรงไหน ทำได้สองแบบ: ผู้เชี่ยวชาญตรวจ (เช่น Heuristic Evaluation) หรือ ผู้ใช้จริงลองใช้ (เช่น Usability Testing) Heuristic Evaluation คือให้ evaluator 3-5 คนตรวจหน้าจอทีละหน้า เทียบกับหลัก 10 ข้อของ Jakob Nielsen แล้วจดปัญหา พร้อมระบุว่าละเมิดข้อไหนและร้ายแรงแค่ไหน ข้อดีคือเร็วและถูก ไม่ต้องหาผู้ใช้ แต่ไม่ใช่ผู้ใช้จริง จึงควรใช้ร่วมกับ Usability Testing

อธิบาย Nielsen’s 10 Heuristics (กดเพื่อดู)

1. Visibility of system status: บอกสถานะให้ผู้ใช้รู้เสมอ

ความหมาย: ระบบต้องบอกว่ากำลังเกิดอะไรขึ้น ภายในเวลาที่เหมาะสม
ดี: แถบความคืบหน้าตอนอัปโหลด, สถานะพัสดุ “กำลังจัดส่ง”
แย่: กดชำระเงินแล้วหน้าจอนิ่ง ไม่รู้ว่าสำเร็จหรือยัง

2. Match between system and the real world: ใช้ภาษาและแนวคิดของผู้ใช้

ความหมาย: พูดภาษาที่ผู้ใช้เข้าใจ เรียงข้อมูลตามลำดับที่เป็นธรรมชาติ ไม่ใช้ศัพท์เทคนิคของระบบ
ดี: ไอคอนตะกร้า ถังขยะ ซองจดหมาย
แย่: ข้อความ “Fatal exception” แทนที่จะบอกว่าอินเทอร์เน็ตหลุด

3. User control and freedom: ออกจากสถานการณ์ที่พลาดได้ง่าย

ความหมาย: ผู้ใช้กดผิดได้เสมอ ต้องมีทางออกฉุกเฉิน ย้อนกลับ ยกเลิก ทำซ้ำ
ดี: Undo, Cancel, ปุ่ม Back, “เลิกส่งอีเมล”
แย่: ขั้นตอนสมัครที่ไม่มีปุ่มย้อนกลับ ต้องกรอกใหม่ทั้งหมด

4. Consistency and standards: สอดคล้องและเป็นไปตามมาตรฐาน

ความหมาย: สิ่งเดียวกันต้องเรียกและทำงานเหมือนกัน และเป็นไปตามแนวปฏิบัติที่ผู้ใช้คุ้นจากแอปอื่น
ดี: โลโก้มุมซ้ายบนกดแล้วกลับหน้าแรก, ไอคอนค้นหาเป็นแว่นขยาย
แย่: หน้าหนึ่งใช้ “บันทึก” อีกหน้าใช้ “ตกลง” “เซฟ” ปนกัน

5. Error prevention: ป้องกันก่อนเกิดข้อผิดพลาด

ความหมาย: ดีกว่าการแจ้ง error ที่ดี คือออกแบบไม่ให้เกิด error เลย
ดี: ถามยืนยันก่อนลบ, ปุ่มส่งใช้ไม่ได้จนกรอกครบ, เลือกวันที่จากปฏิทิน
แย่: ปุ่ม “ลบบัญชี” อยู่ติดปุ่ม “บันทึก” และลบทันทีไม่ถามซ้ำ

6. Recognition rather than recall: ให้เห็นแทนการให้จำ

ความหมาย: ลดภาระความจำ แสดงตัวเลือก คำสั่ง และข้อมูลให้เห็น ไม่บังคับให้จำข้ามหน้า
ดี: ประวัติการค้นหา, autocomplete, รายการล่าสุด
แย่: ต้องจำรหัสสินค้า 8 หลักจากหน้าก่อนมากรอกอีกหน้า

7. Flexibility and efficiency of use: ยืดหยุ่นและเร็วสำหรับผู้ชำนาญ

ความหมาย: มือใหม่ใช้ตามขั้นตอนปกติได้ ส่วนผู้เชี่ยวชาญมีทางลัด
ดี: Ctrl+C / Ctrl+V, การปัดข้ามขั้นตอน, ปรับแต่งเมนูโปรด
แย่: ต้องคลิกผ่าน 5 เมนูทุกครั้งแม้ทำเรื่องเดิมทุกวัน

8. Aesthetic and minimalist design: เรียบง่าย ไม่มีข้อมูลเกินจำเป็น

ความหมาย: ทุกส่วนที่เพิ่มเข้ามาแย่งความสนใจจากสิ่งสำคัญ แสดงเฉพาะสิ่งที่เกี่ยวกับงานที่ทำ (ไม่ได้แปลว่าต้องสวยแค่อย่างเดียว)
ดี: หน้า Google ที่มีช่องค้นหาเด่นชัด
แย่: หน้าแรกอัดแบนเนอร์ โฆษณา และข้อความจนหาปุ่มหลักไม่เจอ

9. Help users recognize, diagnose, and recover from errors: error ต้องช่วยแก้ปัญหา

ความหมาย: ข้อความ error ใช้ภาษาง่าย บอกว่าเกิดอะไรขึ้น และเสนอวิธีแก้
ดี: “รหัสผ่านต้องมีอย่างน้อย 8 ตัว ตอนนี้มี 5 ตัว”
แย่: “Error 500” หรือ “เกิดข้อผิดพลาด” เฉยๆ

10. Help and documentation: ความช่วยเหลือที่หาเจอและทำตามได้

ความหมาย: ระบบดีที่สุดคือใช้ได้โดยไม่ต้องมีคู่มือ แต่ถ้ามีต้องค้นหาง่าย สั้น ตรงกับงานที่ทำ และเป็นขั้นตอน
ดี: ช่องค้นหาใน Help Center, คำแนะนำตอนใช้งานครั้งแรก
แย่: คู่มือ PDF 80 หน้าที่ไม่มีสารบัญ

ข้อ 5: A/B Testing

จำลองการทดลองปุ่มสมัคร A (เดิม) กับ B (ใหม่) ซึ่งโปรแกรมตั้งอัตราจริงของ B ไว้สูงกว่า A เล็กน้อย ลองดูว่าต้องใช้ตัวอย่างเท่าไรจึงมั่นใจได้

เดโม: A/B Test Simulator
A (control)
B (variant)
กด “รันการทดลอง” (สุ่มใหม่ทุกครั้ง ผลจึงต่างกันได้)
เดโม: ทดลองซ้ำ 20 ครั้ง (ดูว่าตัวอย่างน้อยหลอกเราได้แค่ไหน)

ใช้จำนวนตัวอย่างตามสไลเดอร์ด้านบน B ดีกว่า A จริง ดูว่าใน 20 ครั้งเจอผลที่มีนัยสำคัญกี่ครั้ง และกี่ครั้งที่สรุปผิดว่า A ชนะ

ลองตั้งตัวอย่างที่ 100 แล้วเทียบกับ 10,000

ขั้นตอน: ตั้งเป้าหมายและ metric → ตั้งสมมติฐาน → เปลี่ยนตัวแปรเดียว → สุ่มแบ่งผู้ใช้ → รันให้นานพอ → ดูนัยสำคัญ (p < 0.05) → นำผู้ชนะไปใช้
